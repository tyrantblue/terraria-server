## 二、建议补的功能（按优先级）

### P1 运维刚需

1. **定时任务**（最想要的一个）
   * 定时 `save`（比如每 15 分钟，防掉电丢档）；
   * 定时备份 + **自动清理旧备份**（保留最近 N 份 / N 天，现在备份只会越堆越多）；
   * 凌晨低峰定时重启（原版跑久了确实会僵）；
   * 实现成本低：服务里一个 `asyncio` 循环 + 一张任务表，配置写在 `docker-compose.yml` 的
     environment 里即可（和守卫一样的风格）。
2. **备份恢复**
   * 现在能创建/列出备份，但没有「从备份恢复」。
   * 恢复 = 停服 → 覆盖 `.wld` → 启服，天然适合做成操作（`world.restore` → 202）。
   * 顺带把 Terraria 自己生成的 `.wld.bak` / `.bak2` 也纳入统一视图。
3. **日志时间戳 + 轮转**
   * `output.log` 目前**没有时间戳**（`tee -a` 直接落盘），面板只能显示相对顺序，
     排查问题时无法回答「几点被占满的」；
   * 文件无限增长（现在 500KB 级，长期会很大）。
   * 做法：`start.sh` 里给 `tee` 前加时间戳前缀 + 落一份 `/etc/logrotate.d/terraria`。
     注意：加前缀要同步改 `api/app/services/console/parser.py` 的正则与
     `classify_line`（日志格式变更属于接口行为变化，要走 CHANGELOG）。
4. **事件通知**
   * 玩家上线/下线、服务端崩溃、被扫描封禁、自动恢复（假满员）——这些现在只在
     `docker compose logs terraria-guard` 里，没人盯着就不知道。
   * 最省事：一个通用 webhook（Discord / Telegram / 企业微信），
     守卫和 API 各发几个事件即可。

### P2 好用但非必需

5. **白名单/封禁名单的可视化管理**
   * 守卫的白名单现在是 `guard/allow.txt`（手工编辑 + `apply`），面板看不到；
   * 学习型白名单在 `guard/learned_allow.txt`，也没有接口暴露；
   * 封禁名单只能读 `banlist.txt`，`unban` 是原版缺失的能力（已提供按行删除）。
   * 建议：加一组 `/api/v1/guard/*` 接口（读取/增删白名单、查看被封 IP 与剩余时间、
     手动解封），把两侧状态在面板里对齐。
6. **服务器资源与健康曲线**
   * CPU/内存/磁盘、在线人数曲线、崩溃与自动恢复次数。
   * 容器指标可以直接读 cgroup，不需要额外组件；存最近 N 个采样点即可。
7. **操作审计落盘**
   * `POST /api/v1/console/commands` 已有内存审计（最近 200 条），重启即丢。
   * 落一份 `control/audit.log`（JSON Lines）成本很低，出问题能回溯。
8. **世界元信息**
   * 上传的 `.wld` 可以解析出尺寸（小/中/大）、难度、是否专家/大师、创建时间，
   * 面板上看着更直观。需要写一点 `.wld` 头部解析（格式公开，几十行）。
9. **上传的健壮性**
   * 目前没有大小上限、没有磁盘余量检查；
   * 建议加上限（比如 500MB）与 `Content-Length` 预检，避免把磁盘写满。

### P3 想做再说

10. **鉴权**
    * 现状：只有来源 IP 白名单（`DOCKER-USER`），应用层无认证。
    * 单人使用够用；如果以后面板要给别人看，加一个静态 Bearer token 即可（十几行）。
11. **TShock**
    * 需要权限组/领地/商店/反作弊才值得换；原版世界文件兼容，但改动面不小。
12. **多世界同时在线 / 多实例**
    * 当前是单实例单世界，架构上没必要改动。

## 三、刻意不做的

* **通用 SQL/ORM**：状态都在文件和控制台里，加数据库只会增加迁移负担。
* **用户体系/多租户**：一个人用，没有收益。
* **把守卫逻辑搬进 API 进程**：守卫需要宿主机 netfilter 权限，独立容器更干净
  （见 `connection-guard.md`）。

---

## 四、建议的下一步顺序

1. 定时任务（保存/备份/清理/重启）——运维收益最大，实现最直接。
2. 备份恢复 + `.bak` 统一视图。
3. 日志时间戳与轮转（顺带让控制台的 `kind`/时间线更准）。
4. 事件通知（webhook）。
5. 前端迁移到 `/api/v1`（后端已经双跑，`/api/meta/usage` 能看到旧接口还剩多少调用）。
