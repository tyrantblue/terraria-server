# API v1 参考（给前端）

**2.0.0 起这是唯一的接口面**：旧的 `/api/*` 资源路由已删除（返回 404）。
完整的变更与迁移对照见 [`CHANGELOG.md`](CHANGELOG.md)。

约定：

* 基础地址 `https://terraria-api.tyrantblue.xyz`（或直连 `http://<VPS>:8080`）。
* 请求/响应都是 JSON；上传世界用 `multipart/form-data`。
* 成功**直接返回资源本体**，不再包 `{"success": true}`。
* 失败统一：

  ```json
  { "detail": "player not online: foo",
    "error": { "code": "not_found", "message": "player not online: foo", "details": {} } }
  ```

  `code` 是稳定字符串（`bad_request` / `not_found` / `operation_not_found` /
  `conflict` / `forbidden` / `unauthorized` / `validation_failed` /
  `client_outdated` / `too_many_requests` / `upstream_failed` /
  `payload_too_large` / `insufficient_storage` / `console_unavailable` /
  `console_busy` / `console_timeout`），前端按它分支即可；`details` 可选。
* `422` 的 `detail` 是 pydantic 的**错误数组**（不是字符串，为兼容旧客户端保留），
  但 `error.code` 同样是稳定的 `validation_failed`，程序判断请用后者。
* 可以带 `X-Client-Version: <面板构建版本>`，服务端会在响应里原样回显（排障用），
  并且**低于 `min_client_version` 时直接拒绝**（见 §0）。
* `message` / `error.message` / `detail`（字符串形式）是**面向人的回退文案，当前为中文，
  不保证稳定、不要用于程序判断**；程序判断请用 `code` / `state` / `error.code`。

## 0. 认证、CORS 与限流

API 默认假定鉴权在边缘完成（Cloudflare Access / VPN / 受限反向代理，见根 README
「Security」）。后端自身也提供两道可选的加固，按需在 `docker-compose.yml` 里开启：

| 环境变量 | 默认 | 作用 |
| --- | --- | --- |
| `TERRARIA_API_TOKEN` | 空（关闭） | 非空时，**写操作**（POST/PUT/PATCH/DELETE）必须带 `Authorization: Bearer <token>` 或 `X-API-Token: <token>`；否则 **401** `unauthorized`。GET 不受影响。 |
| `TERRARIA_CORS_ORIGINS` | `*` | 逗号分隔的允许来源。生产部署应收敛为面板实际来源，例如 `https://terraria-api.tyrantblue.xyz`。 |
| `TERRARIA_RATE_LIMIT_ENABLED` | `1` | 是否启用写操作限流（进程内滑动窗口，60 秒）。 |
| `TERRARIA_RATE_LIMIT_WRITE_PER_MINUTE` | `120` | 普通写操作上限（每客户端）。 |
| `TERRARIA_RATE_LIMIT_CONSOLE_PER_MINUTE` | `60` | `POST /api/v1/console/commands` 的上限。 |
| `TERRARIA_RATE_LIMIT_RESTART_PER_MINUTE` | `12` | `POST /api/v1/server/restart` 的上限。 |

* 超限返回 **429** `too_many_requests`，`error.details = {bucket, limit, window_seconds,
  retry_after}`，并带 `Retry-After` 头。
* **客户端版本门槛**：带 `X-Client-Version` 且低于 `min_client_version`（当前 `1.4.1`）
  时，除 `/api/meta` 与 `/api/health` 外的请求返回 **426** `client_outdated`
  （`details` 给出 `client_version` / `min_client_version`）。不带头（脚本/curl）不拦；
  完全不含数字的自定义版本串（如 `dev`）也放行——这是兼容性提示，不是安全边界。
* CORS 允许任何来源时仍会 `expose_headers: X-Client-Version`，面板读回显不会被浏览器拦。
* 限流器是**进程内**的：多副本部署要换成共享存储（如 Redis），否则每副本各算一份。
* 限流按 `request.client.host` 计数。如果 API 在反向代理后面而 uvicorn 没启用
  `--proxy-headers`，所有请求会共用代理的地址（相当于一个桶）。要在代理后按真实
  客户端 IP 限流，请在 uvicorn 上启用 `--proxy-headers` 并正确配置
  `--forwarded-allow-ips`（只信任你的代理），或直接把限流放在边缘。


## 1. 握手与元信息

### `GET /api/meta`
面板启动时调一次。

```json
{
  "api_version": "2.1.0",
  "min_client_version": "1.4.1",
  "server_version": "1.4.5.8",
  "capabilities": ["server.status", "world.metadata", "config.password_masked",
                   "console.audit.persistent", "server.log_health", "server.metrics",
                   "guard.state", "scheduler.jobs", "backups.list",
                   "notifications.status", "meta.handshake", ...],
  "capability_since": { "guard.state": "2.1.0", "world.metadata": "2.0.0", ... },
  "operation_kinds": [
    { "kind": "server.restart", "label": "Restart server" },
    { "kind": "world.activate", "label": "Switch world" },
    { "kind": "world.restore", "label": "Restore backup" },
    { "kind": "world.backup", "label": "Back up worlds" }
  ],
  "exclusive_operation_kinds": ["server.restart", "world.activate", "world.restore"],
  "deprecations": [],
  "links": { "openapi": "/openapi.json", "docs": "/docs", "changelog": "https://..." }
}
```

* `api_version` **遵循 semver**：patch = HTTP 契约没变（内部修复/新定时任务/新事件类型），
  minor = 有新增（用 `capabilities` 判断），major = 有删除/变更。
  **只有 `min_client_version` 高于面板版本才是"必须升级"的硬条件**，
  不要因为 patch 差异弹提示。
* 2.1.0 起 `min_client_version` 是 `1.4.1`，并且后端会**强制**它（见 §0）：
  1.4.1 是采用 2.0 密码语义（「留空=不修改」）的面板版本。
* `capabilities` 用来做功能开关（老后端没有的新能力别渲染）；它是**只增不减**的
  名字数组，新增能力属于 minor。
* `capability_since` 给出每项能力的引入版本：老后端缺这项能力时，面板可以把提示
  写成「需要 API ≥ x.y」，而不是笼统的「不支持」。
* `operation_kinds` / `exclusive_operation_kinds` 是后端发布的**词汇表**：面板不必
  硬编码 `kind` → 文案映射，也不必自己维护互斥集合。互斥语义见 §7。
* `deprecations` 字段仍然存在，但**恒为 `[]`**（旧接口已经删完，没有可弃用的东西了）。
* `timezone` / `capabilities` 之外的字段都可能为 null，渲染时注意空值。

**能力表**（与 `app/api/system.py` 的常量一致，测试会锁住两边同步）：

| 能力 | 含义 | 引入版本 | 缺失时面板应如何降级 |

## 2. 服务器状态

### `GET /api/v1/server`
**一次拿全**，取代旧版「`/api/server/status` + 7 个查询型 POST + `/api/world/list`」。

```json
{
  "running": true,
  "version": "1.4.5.8",
  "port": 7777,
  "max_players": 255,
  "time": "4:20 PM",
  "seed": "3.3.1.0.1269458679",
  "motd": "Fly to the sky…Fire bird! Join the RED TEAM, PLZ!!!",
  "players": {
    "online": 2,
    "max": 255,
    "players": [
      { "name": "ユノの犬", "ip": "203.0.113.10", "port": 26557 },
      { "name": "CTQ", "ip": "198.51.100.30", "port": 44176 }
    ]
  },
  "world": { "file": "gogogo.wld", "name": "gogogo", "size": 12300762,
             "modified_at": 1789000000.0, "active": true,
             "metadata": { "format_version": 279, "size_tier": "medium",
                           "width": 6400, "height": 1800,
                           "difficulty": "master",
                           "created_at": "2026-09-01T12:00:00Z" } },
  "config": { "maxplayers": "255", "motd": "...", "port": "7777", "world": "/worlds/gogogo.wld",
              "password": "••••••" },
  "password_set": true,
  "log_stalled": false,
  "log_age": 2.4
}
```

字段可能是 `null`（服务端刚重启、控制台暂时读不到）。`time`/`players` 最多有 3 秒缓存，
`version/port/max_players/seed/motd` 属于静态字段（服务端重启或改过配置才会刷新）。

**`running` 是真实探测结果**（不是硬编码的 `true`）：以能否从控制台读到回显为准。

* 服务端已退出 / 控制台不可用时，接口仍然返回 **200**：`running: false`，`version` /
  `port` / `max_players` / `time` / `seed` / `motd` 为 `null`（有缓存时给缓存值），
  `players.online = 0`，`config` / `world` 照常返回（它们来自文件，不依赖游戏进程）。
  以前这种情况会 **500**，面板把「游戏服停了」误报成 "API Unreachable"。
* 因此面板应把 `running` 当作「游戏服是否在线」的唯一依据，而不是把非 2xx 当作掉线。
* 停服期间 `log_stalled` 恒为 `false`，不要因为拿不到 `version` 就误报日志停更。

**敏感字段不回显明文**：`config.password` 永远是掩码 `••••••`（未设密码时是 `""`），
是否已设置看 `password_set`。改密码请用 `PUT /api/v1/config`（见 §5）。

**日志管道健康**（能力 `server.log_health`）：

* `log_age`：`output.log` 最后一次写入距今多少秒（文件不存在时为 `null`）。
* `log_stalled`：控制台心跳探测失败（哨兵写进去了但读不到回显），
  或者「能读到版本、日志却超过 `LOG_STALL_SECONDS`（默认 120 秒）没有新内容」。
  两种情况都表示面板即将读不到状态（游戏可能还能玩）。
  判定为 `true` 后会保持 15 分钟，直到下一次探活成功才清零。
* 服务端正在重启 / 切换世界时恒为 `false`（那期间的安静是正常的），不会误报。

`world.metadata`（能力 `world.metadata`）来自 `.wld` 文件头，解析失败时为 `null`：

| 字段 | 说明 |
| --- | --- |
| `format_version` | 世界文件版本（如 `279`） |
| `size_tier` | `small` / `medium` / `large`（非官方尺寸按宽度归类） |
| `width` / `height` | 世界格数（官方小=4200×1200、中=6400×1800、大=8400×2400） |
| `difficulty` | `classic` / `expert` / `master` / `journey` |
| `created_at` | ISO-8601（UTC）；拿不到时为 `null` |

### `POST /api/v1/server/actions`
```json
{ "action": "save" }      // 或 "settle"
```
→ `{"ok": true}`

### `POST /api/v1/server/restart` → **202**
保存 → 关服 → 等待重新监听，全程后台执行：
```json
{ "operation_id": "8f3c1a9b2d4e", "state": "pending", "kind": "server.restart",
  "poll": "/api/v1/operations/8f3c1a9b2d4e" }
```

* `poll` 是**按请求生成的真实 URL**（不是模板字符串），面板可以直接 GET 它看进度；
  也可以自己用 `operation_id` 拼（见 §7）。
* **只对正在运行的服务端起效**：如果游戏服已经退出（`running: false`），FIFO 没有
  读者，重启操作会失败并提示「服务端当前未在运行」。拉起已退出的容器请用
  `docker compose restart terraria`（见根 README「Restart」）。面板应据此调整文案，
  而不是让用户以为 API 能凭空拉起进程。

### `POST /api/v1/server/time`
```json
{ "phase": "noon" }       // dawn | noon | dusk | midnight
```
→ `{"phase": "noon", "time": "12:00 PM"}`

### `GET /api/v1/metrics?minutes=60`
资源与在线人数曲线（后端每 `METRICS_INTERVAL_SECONDS` 采一个点，默认 60 秒；
内存保留 `METRICS_RETENTION_POINTS` 个点，默认 1440 = 24 小时）。

```json
{
  "interval_seconds": 60.0,
  "retention_points": 1440,
  "window_minutes": 60.0,
  "latest": { "ts": 1789700000.0, "cpu_percent": 12.5, "cpu_cores": 2.0,
              "memory_bytes": 66674688, "memory_limit_bytes": null,
              "disk_free_bytes": 21474836480, "disk_total_bytes": 53687091200,
              "players_online": 2 },
  "points": [ { "ts": 1789699940.0, "...": "同上" } ]
}
```

* `points` 按时间**升序**；`?minutes` 上限 1440。
* 字段可能为 `null`：非 Linux/cgroup 环境拿不到 CPU/内存，`memory_limit_bytes`
  为 `null` 表示容器没设内存上限。画曲线时空点跳过即可。
* 采样点只在内存里（API 重启后从零开始）——这是近期曲线，不是长期监控存储。
* 读哪些值：CPU 是「累计 CPU 时间」的差值，已按容器可用核数折算（100% = 吃满分配
  的核）；`cpu_cores` 就是那个折算基数（来自 `cpu.max` 配额或 `cpuset`）。
* `METRICS_INTERVAL_SECONDS=0` 可以关掉采样，此时 `points` 恒为空数组。

## 3. 玩家与广播

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/players` | `{online, max, players:[{name,ip,port}]}` |
| POST | `/api/v1/players/{name}/kick` | 玩家不在线 → **404** `not_found` |
| POST | `/api/v1/players/{name}/ban` | 同上；底层是控制台 `ban` |
| DELETE | `/api/v1/players/{name}/ban` | 从 `banlist.txt` 移除；不在名单 → **404** |
| GET | `/api/v1/bans` | `{bans:[...], source, exists, note}` |
| POST | `/api/v1/broadcast` | `{"message":"..."}` → `{"ok":true}` |

`{name}` 需要 URL 编码（玩家名可能含空格/日文，例如 `%E3%83%A6...`）。

关于封禁：原版控制台**只有 `ban` 没有 `unban`**，而且只会给「当前在线」的玩家写名单；
`banlist.txt` 在第一次封禁之前不存在（此时 `exists=false`、`note` 会说明）。
`DELETE` 是按行改写文件，因此可以移除不在线的历史封禁。

> **并发说明**：`DELETE` 用「唯一临时文件 + `banlist.txt.lock` 上的 flock」串行化，
> 所以多个 API 请求同时删/追加不会互相覆盖；`os.replace` 前还会再确认文件没变。
> 但**游戏进程自己**追加封禁时不持这把锁，理论上仍有一个极小的窗口会丢掉那次追加
> （这是原版文件协议的固有限制）。删完可以 `GET /api/v1/bans` 复核一次。

## 4. 控制台

### `GET /api/v1/console?tail=200` 或 `?since=<cursor>`

```json
{
  "lines": [
    { "offset": 524288, "ts": 1789636035.0, "kind": "player_join",
      "text": "[2026-09-17 17:07:15] : ユノの犬 has joined." },
    { "offset": 524310, "ts": 1789636035.0, "kind": "chat",
      "text": "[2026-09-17 17:07:15] : <ユノの犬> 加油" }
  ],
  "cursor": 524340
}
```

`ts` 是由 `start.sh` 打在行首的 `[YYYY-mm-dd HH:MM:SS]` 解析出来的 epoch（秒）；
旧日志没有时间戳时为 `null`。`text` 保留原始内容（含时间戳前缀）。

* `kind`：`player_join` `player_leave` `connect` `disconnect` `boot` `chat`
  `world_save` `startup` `error` `prompt` `output` `blank`。
  面板可直接按 `kind` 上色/过滤，不必自己正则。
* **增量拉取**：把上一次的 `cursor` 作为 `since` 传回来，只拿新行。
* 服务端内部使用的哨兵回显已被过滤，不会出现。

### `WS /api/v1/console/stream`
连接后先收到最近约 100 行**历史回放**（`console.line` 帧），然后是
`{"type":"hello","cursor":N}`，之后持续推送新行：

```json
{ "type": "console.line", "offset": 524340, "ts": 1789636035.0, "kind": "chat", "text": ": <CTQ> hi" }
{ "type": "hello", "cursor": 524341 }
```

* **`offset` 在回放和实时帧里是同一个语义**：真实的行起始字节偏移，来自同一个日志文件。
  可以直接拿它当去重键 / React key（`Map<offset, line>`），不需要为回放做特殊分支。
  回放帧的 `offset` 一定 `< hello.cursor`；`offset >= hello.cursor` 的行属于
  「回放期间新增」，由实时循环补发，既不会重复也不会丢。
* `hello` 仍然**最后**发（顺序与 1.x 一致，前端不用改解析逻辑）。它是权威续传点：
  断线重连后先 `GET /api/v1/console?since=<上次的 cursor>` 补洞，再连 WS。
* 服务端内部使用的哨兵回显已被过滤，不会出现。

### `POST /api/v1/console/commands`
```json
{ "command": "seed" }
```
→ `{ "ok": true, "command": "seed", "output": "World Seed: 3.3.1.0.1269458679\n" }`

**白名单**：`help save settle playing version port maxplayers time seed motd password
kick ban say dawn noon dusk midnight`。
`exit` / `exit-nosave` 一律 **403**（关服请用 `/api/v1/server/restart`，它会保存并等待恢复）。
每次调用都会记进审计。

### `GET /api/v1/console/audit`
`{entries:[{ts, command, actor}]}`，最近 200 条。

## 5. 配置（持久化 vs 运行时）

### `GET /api/v1/config`
```json
{
  "values": { "motd": "...", "maxplayers": "255", "port": "7777", "world": "gogogo.wld",
              "password": "••••••" },
  "password_set": true,
  "editable_keys": ["autocreate","difficulty","language","maxplayers","motd","npcstream",
                    "password","port","priority","seed","secure","upnp","world","worldname"],
  "runtime_keys": ["maxplayers","motd","password"],
  "restart_keys": ["autocreate","difficulty","language","port","secure","seed","upnp",
                   "world","worldname"],
  "path": "/opt/terraria/config/serverconfig.txt"
}
```

**`password` 不回显明文**：已设置时 `values.password` 是掩码 `••••••`，未设置时是 `""`，
两种情况都用 `password_set` 明确区分。面板应当：

* 密码输入框**留空** + placeholder「留空表示不修改」；
* 只有用户真的输入了内容，才把 `password` 放进 `PUT` 的 body。

### `PUT /api/v1/config`
```json
{ "values": { "motd": "hello", "maxplayers": 255 }, "apply": true }
```

* **总是写进 `serverconfig.txt`**（持久化，重启不丢）；写入是原子的，注释与顺序保留。
* `apply=true` 时，`runtime_keys` 里的项会立刻用控制台命令生效。
* **重启类键只有文件真的变了才会**顺带提交一次重启操作（响应变成 **202**）。
  把整份表单原样 PUT 回来（`restart_keys` 的值都没变）**不会**触发重启——需要让
  已落盘的重启类值重新生效，请显式调用 `POST /api/v1/server/restart`：

```json
{ "persisted": ["port","motd"], "changed": ["port","motd"], "applied": ["motd"],
  "requires_restart": ["port"], "operation_id": "8f3c1a9b2d4e" }
```

* **`persisted` 与 `applied` 的语义**（issue #9）：

  * `persisted`：本次真正写进 `serverconfig.txt` 的键（只要请求带了就写，幂等）；
  * `changed`：**文件里**确实发生了变化的键（文件已经是目标值时为 `[]`）；
  * `applied`：本次**成功对齐到运行态**的 `runtime_keys`；
  * `requires_restart`：**文件里发生了变化、需要重启才生效**的 `restart_keys`
    （`changed ∩ restart_keys`）；`apply=false` 时它只是提示，`apply=true` 时后端会
    据此提交重启并把 `operation_id` 一并返回。

* `apply=true` 时**无条件**对齐请求里的 `runtime_keys`，与文件是否变化无关：
  这样「文件已写入、上次 apply 失败」的请求可以原样重试，不会被误判成
  `changed=[]` 而返回 200 + `applied=[]` 的假成功。
* apply 失败时返回 **503**（或相应的控制台错误），并在 `error.details` 里给出
  已经落盘但**尚未生效**的部分，方便面板提示「已保存，未生效，可重试」：

  ```json
  { "detail": "控制台暂时不可用",
    "error": { "code": "console_unavailable", "message": "…",
               "details": { "persisted": ["motd"], "applied": [],
                            "pending": ["motd"] } } }
  ```

* 校验失败 → **400**（`details.editable_keys` 列出允许的键）。
* **`password` 的三态语义**（掩码之后必须写死，别再靠"猜"）：

  | 请求里 | 结果 |
  | --- | --- |
  | 不带 `password` 键 | **不修改**（前端没碰输入框时就别带这个键） |
  | 带非空值（如 `"s3cret"`） | 设为该密码 |
  | 带空字符串 `""` | **清空密码**（`serverconfig.txt` 写成 `password=`，`apply=true` 时立刻生效；面板的「留空即移除」就是这条） |
  | 带掩码 `"••••••"` | **400** `bad_request`（`details.key="password"`）——防止把 `GET` 的结果原样 `PUT` 回来 |

  清空是**显式**动作：只有真的带上传空字符串才会清；省略该键永远是「不改」。
  当前面板的密码框初始为空、只有用户输入才提交，所以两者不会互相误伤。
* **`maxplayers` 小于 64 需要二次确认**：

  ```json
  { "values": { "maxplayers": 8 } }
  ```
  → **409** `conflict`，
  `error.details = { "requested": 8, "recommended_min": 64, "reason": "phantom-full" }`

  原因见 [`../connection-guard.md`](../connection-guard.md)：原版会把每条陌生 TCP
  连接都算进 `maxplayers`，8 个槽位很容易被扫描流量拖成「假满员」。
  面板应弹确认框，确认后带上 `"confirm_low_max_players": true` 再发一次。

## 6. 世界与备份

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/worlds` | `{worlds:[{file,name,size,modified_at,active,metadata}], active_world, backup_dir}` |
| POST | `/api/v1/worlds` | multipart `file=@x.wld` → **201** `{name,file,size}`；同名 **409**（`details.file` 是文件名）；超限 **413** `payload_too_large`；磁盘不足 **507** `insufficient_storage` |
| DELETE | `/api/v1/worlds/{file}` | 删除；**当前激活的世界不能删** → 409；不存在 → 404 |
| POST | `/api/v1/worlds/{file}/activate` | **202** `{operation_id,state,kind,poll}` |
| POST | `/api/v1/worlds/{file}/backup` | **202**；把该世界（或全部）与 `serverconfig.txt` 复制到 `backup/<时间戳>/`；恢复进行中 → **409** |
| GET | `/api/v1/backups` | `{backups:[{name,created_at,files,size,kind,restorable,path}]}` |
| POST | `/api/v1/backups/{name}/restore` | **202** 从备份恢复整个世界 |

`kind` 有三类：`manual`（面板/定时任务创建的 `20260917-170849`）、
`auto`（Terraria 自己写的 `.wld.bak`/`.bak2`，名字形如 `auto:gogogo.wld.bak`）、
`legacy`（迁移时留下的 `config-*`/`worlds-*`）。

`metadata` 的字段说明见 §2（解析失败为 `null`，接口不会因此失败；
上传成功后列表里就能看到尺寸/难度，不必等重启）。

**恢复**（`POST /api/v1/backups/{name}/restore`，body 可带 `{"file": "WSD.wld"}`）：

* 恢复的是**当前激活的世界**时，服务端会重启两次：保存 → 存安全副本 →
  停服 → 覆盖文件 → `exit-nosave` 启动（第二次不保存，否则会把刚恢复的文件覆盖回去）。
  全程约 40~90 秒，用 `operation_id` 看进度。
* 恢复**非激活的世界**只复制文件，不重启。
* 覆盖前会在 `backup/pre-restore-<时间戳>/` 留一份安全副本，结果里返回该路径。
* 多世界备份需要显式指定 `file`，否则 **400** 并返回 `error.details.candidates`。
* 备份名做路径校验，`../` 之类一律拒绝。

## 7. 长任务

任何返回 **202** 的接口都给出了 `operation_id` 与 `poll`（真实 URL）：

### `GET /api/v1/operations/{id}`
```json
{
  "id": "8f3c1a9b2d4e",
  "kind": "world.activate",
  "kind_label": "Switch world",
  "state": "running",
  "progress": 65,
  "message": "等待服务端重新监听",
  "message_code": "activate.waiting_listen",
  "message_params": {},
  "created_at": 1789000000.0,
  "started_at": 1789000000.1,
  "finished_at": null,
  "result": null,
  "error": null
}
```
`state`：`pending` → `running` → `succeeded` | `failed`。
建议轮询间隔 500ms~1s，`state` 进入终态就停。`kind`：`server.restart` /
`world.activate` / `world.restore` / `world.backup`。

**结构化文案**（issue #18）：`message` 是中文自由文本回退（**不保证稳定**），
`message_code` / `message_params` 才是给程序判断与本地化的稳定字段，命名形如
`<kind 短名>.<动作>`：

| `message_code` | 含义 |
| --- | --- |
| `pending` / `running` / `succeeded` / `failed` | 与 `state` 对应的通用文案（终态也有 code） |
| `restart.saving_world` / `restart.stopping_server` / `restart.waiting_listen` / `restart.server_up` | 重启各阶段 |
| `activate.preparing` / `activate.writing_config` / `activate.stopping_server` / `activate.waiting_listen` | 切世界各阶段 |
| `restore.saving_world` / `restore.safety_copy` / `restore.restarting` / `restore.writing_world` / `restore.restarting_again` / `restore.waiting_listen` | 恢复各阶段 |
| `backup.copying` / `backup.done` | 备份各阶段 |

`message_params` 携带参数（如 `{"file": "gogogo.wld"}`、`{"name": "pre-restore-…"}`），
不要把参数拼进 code。`kind_label` 与 `/api/meta` 的 `operation_kinds` 是同一份词汇表。

### `GET /api/v1/operations`
最近 **50** 条（新的在前），响应里附 `in_flight`（未到终态的数量）。支持
`?state=pending|running|succeeded|failed` 过滤。

* **保留策略**：只存在 API 进程内存里，最多 50 条，超出后按提交顺序淘汰最旧的，
  **API 重启即清空**；不按时间/状态裁剪，也没有历史落盘。
* **不存在的 operation** → **404** + `error.code = "operation_not_found"` +
  `error.details.operation_id`（与「路由不存在」的 `not_found` 区分开）。
  面板应把 `operation_not_found` 当成「结果未知，不要自动重试」，先确认服务端当前状态。
* 路由本身不存在仍是 `not_found`，两者可区分。

**互斥**：`server.restart` / `world.activate` / `world.restore` 这几类会动服务端进程/
世界文件，同一时刻只允许一个（与 `/api/meta` 的 `exclusive_operation_kinds` 一致）；
重复提交会得到 **409** `conflict`，`error.details.operation_id` 是正在跑的那个，
`error.details.kind` 是它的类型。另外 **`world.restore` 进行中会拒绝 `world.backup`**
（409），避免备份读到被覆盖到一半的世界文件。
`config.apply` 不是真实存在的 kind（配置生效走 `server.restart`），已从文档与集合里删除。

## 8. 定时任务

配置在 `docker-compose.yml` 的 `SCHEDULE_*`（见仓库根 README 的「定时任务」一节）。

### `GET /api/v1/scheduler`
```json
{
  "enabled": true,
  "timezone": "Asia/Shanghai",
  "jobs": [
    { "name": "save", "kind": "interval", "description": "每 15 分钟保存一次世界",
      "enabled": true, "interval_seconds": 900, "at": null,
      "next_run": 1789637000.0, "last_run": 1789636100.0,
      "last_status": "skipped", "last_detail": "skipped: 无人在线",
      "last_code": "skipped.no_players", "last_params": { "online": 0 },
      "run_count": 12, "skipped_count": 9, "failed_count": 0,
      "history": [{ "at": 1789636100.0, "status": "skipped",
                    "detail": "skipped: 无人在线", "code": "skipped.no_players",
                    "params": { "online": 0 }, "duration": 0.1, "manual": false }] }
  ]
}
```
`last_status`：`succeeded` | `skipped`（附原因）| `failed`。
`last_detail` / `history[].detail` 是中文自由文本回退（**不保证稳定**）；
程序判断请用稳定的 `last_code` / `history[].code`：`ok` / `stalled` /
`unavailable.busy` / `unavailable.console` / `error` / `skipped.no_players` /
`skipped.players_online` / `skipped.console_unavailable` / `submitted` / `backup.done`，
参数在 `params` 里（如 `submitted` 带 `params.operation_id`）。

### `POST /api/v1/scheduler/{name}/run`
手动触发一次，同步返回本次结果（`save`/`backup` 通常几百毫秒）。不存在的任务名 → **404**。

`restart` 这类会提交后台 operation 的任务，响应带**顶层** `submitted`，面板据此去轮询
`/api/v1/operations/{id}` 展示进度，而不是立刻宣告完成（issue #10）：

```json
{ "at": 1789636100.0, "status": "succeeded", "detail": "submitted: 8f3c1a9b2d4e",
  "code": "submitted", "params": { "operation_id": "8f3c1a9b2d4e" },
  "submitted": "8f3c1a9b2d4e", "duration": 0.2, "manual": true }
```

* `submitted` 等于 `/api/v1/operations` 里对应 operation 的 `id`（仅 `restart` 类任务有）。
* 不要再用正则从 `detail` 里抠 operation id，也不要靠 `detail.startsWith('skipped')`
  判断状态——用它旁边的 `code`。

## 9. 事件通知

### `GET /api/v1/notifications`
```json
{
  "enabled": true,
  "url": "https://discord.com/…",
  "format": "auto",
  "events": "all",
  "deliveries": [
    { "ts": 1789636100.0, "event": "player_join", "title": "ユノの犬 加入了游戏",
      "ok": true, "status": 204, "error": null }
  ]
}
```
webhook URL 只回显主机名（它本身就是凭据）。`events` 为 `all` 或事件名列表。

### `POST /api/v1/notifications/test`
同步投递一条测试消息，返回投递结果——配置完 webhook 用它验证最方便。

事件类型：`player_join`、`player_leave`、`player_booted`、`server_up`、`server_error`、
`backup_done`、`schedule_failed`、`restart_skipped`、`log_stalled`。

`log_stalled`：控制台心跳判定日志管道停更时发出（见 §2 的 `log_stalled` / `log_age`）。
1.4.2 时它叫 `console_stalled`，2.0.0 起改名——`NOTIFY_EVENTS` 里写死过旧名字的要同步改，
否则这条告警会被白名单过滤掉。恢复手段：先 `save`，再 `docker compose restart terraria`。

`NOTIFY_FORMAT=auto` 会按 URL 识别 **Discord / Slack / 飞书**，都不是则发通用 JSON。
飞书用 `{"msg_type":"text","content":{"text":...}}`；由于飞书 HTTP 状态码恒为 200，
后端会额外解析响应体的 `code`，把它当成真正的投递结果。

## 9.1 连接守卫

守卫（`terraria-guard` 容器）拿着 ipset/NET_ADMIN 权限，API 通过共享的
`control/` 目录与它通信，所以这里的接口都是同步的（内部等守卫确认，约几百毫秒）。

### `GET /api/v1/guard`
```json
{
  "available": true,
  "stale": false,
  "age": 0.2,
  "updated_at": 1789639000.0,
  "port": 7777,
  "allowlist_only": false,
  "allow": [
    { "ip": "198.51.100.30", "source": "static",  "expires_at": null },
    { "ip": "203.0.113.10", "source": "learned", "expires_at": 1790243800.0 }
  ],
  "banned": [ { "ip": "203.0.113.9", "expires_at": 1789642600.0 } ],
  "counters": { "bans_total": 9, "commands_total": 12,
                "learned_total": 2, "degraded_console": 0 }
}
```

* `available: false` 表示守卫容器的状态文件不存在或已过期（>30 秒没更新）。
  接口仍然返回 **200**，面板可以显示「守卫已停止」，不用处理 5xx。
* **`available: false` 时其余字段依然存在**：`allow` / `banned` 是空数组，
  `counters` 是四项全 0 的完整对象。契约上 `GuardState` 与 `GuardCounters`
  的**所有**字段都是必填——客户端不需要写 `guard.allow ?? []` 这类兜底，
  `available` 只用来切换文案。
* `source`：`static` 来自 `guard/allow.txt`，`learned` 是玩家登录后自动加入的。

### 操作

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/v1/guard/bans` | `{"ip": "1.2.3.4", "seconds": 3600}`；`seconds` 省略用默认（1 小时） |
| DELETE | `/api/v1/guard/bans/{ip}` | 解封（同时清掉内部计数，避免立刻被重新封） |
| POST | `/api/v1/guard/allow` | 加入白名单：**写 `guard/allow.txt`** 并立即生效 |
| DELETE | `/api/v1/guard/allow/{ip}` | 移出白名单（静态与学习型都清） |
| POST | `/api/v1/guard/reload` | 按白名单文件重新同步 ipset |

返回 `{"ok": true, "message": "…", "command_id": "…"}`。
守卫进程/控制文件确实不可用时 **503** `guard_unavailable`；
**IP 格式非法是输入错误 → 400** `bad_request`（`details.ip` 是原值），
不要把它显示成「守卫没在运行」让人去排查一个不存在的问题（issue #16.4）。
